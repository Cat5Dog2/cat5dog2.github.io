## 題材と目的

過去のSEO・CMS実務で「あれば便利だった」ワークフローを題材にしています。キーワード入力から見出し構成、本文生成、記事編集、WordPress投稿、通知までを、一連のワークフローとして扱えるようにすることが目的です。

## 主な機能

- キーワードからの見出し構成・本文生成（Gemini）と、生成ジョブの進捗表示
- Web検索・X投稿検索による参考情報の収集
- 記事の編集・管理と、WordPressへの投稿
- 複数記事の一括作成と、一括生成の進捗確認
- Discordへの通知
- Identityによる認証と、利用者ごとのデータ分離

- **Caddy**: リバースプロキシとしてTLSとヘルスチェックを担当
- **Blazor Web App**: 記事管理UIとIdentity認証を提供し、AI生成などの時間がかかる処理はBackgroundServiceの非同期ジョブへ分離
- **PostgreSQL**: 記事、ジョブ、設定データを永続化
- **外部連携**: Gemini（本文生成）、検索API・X API（情報収集）、WordPress（投稿）、Discord（通知）

## 設計判断とトレードオフ

要件定義書・基本設計書に記録した判断と、その判断で引き受けた制約です。

### WebアプリとBackgroundServiceを1つのコンテナで動かす

要件で初期構成を単一VPS上のDocker Compose運用と定め、MVPではBlazor Web App・API・BackgroundServiceを1つの`app`コンテナに同居させています。専用のキュー基盤は置かず、PostgreSQLの行ロックで、複数のワーカーが同じジョブを取得しないようにしています。

- **引き受けた制約**: 生成ジョブはWebと同じプロセスの資源を使う。ジョブ量が増えた場合は、同じイメージから`worker`コンテナを分離する

### 画面ごとにSSRとInteractive Serverを使い分ける

初期表示・一覧・設定画面はSSRを基本とし、記事編集・見出しの並び替え・ジョブ状態の更新など操作が多い画面だけInteractive Serverを使います。

- **引き受けた制約**: Interactive Serverの画面はSignalRの接続に依存するため、接続が切れた場合や再接続時の扱いを考慮する必要がある

### 公開するポートをCaddyだけに絞る

Docker Composeでは`caddy`だけが80/443を公開し、PostgreSQLとアプリのポートは外部に公開しません。本番の秘密情報はVPS側の環境変数で渡し、リポジトリには含めません。

- **引き受けた制約**: 単一VPSのため、サーバー障害時はアプリ全体が止まる。DBは`pg_dump`によるバックアップを基本とし、手順を運用設計書で定めている

## ゲストログインの設計

公開環境は誰でも試せるようにしつつ、外部APIの費用発生や不正利用、WordPress・Discordへの意図しない送信は防ぐ必要があります。そこで、ゲストも通常ユーザーと同じ画面・処理を使い、外部との接続だけをサンプル応答へ切り替える設計にしました。

- 登録不要のゲストログインにもCSRF検証とログイン用のレート制限を適用し、Admin権限を持たない一般ユーザーとして作成
- 外部APIクライアントをユーザー単位でサンプル応答へ切り替え、Gemini・検索API・X API・WordPress・Discordの実APIには接続しない。バックグラウンドジョブでは、Cookieや入力内容に頼らず、DBに保存したジョブ所有者の情報からゲストかどうかを判定
- データはユーザーIDで分離し、セッションは永続化・延長なしの8時間。期限を迎えたゲストのアカウントと関連データは、バックグラウンド処理が1分ごとに確認して物理削除（処理中のジョブがある場合は完了後）

## 制約と今後の課題

- ゲストの生成・検索結果はサンプル応答。実APIとの連携は通常ユーザーだけが使える
- Gemini以外のAIプロバイダー、CSVインポート、WordPress投稿時のアイキャッチ画像指定、ライター権限は後続フェーズの対象
- 生成ジョブが増えた場合は、`worker`コンテナの分離を検討する
