## 解決したい課題

- 体重や体調などの日々の記録が分散し、変化を追いにくい
- 通院予定、診療内容、処方などを時系列で振り返りにくい
- ペットごとの画像と健康情報を安全に管理する必要がある
- 個人開発でも、デプロイ後の不具合や設定漏れを検知できる仕組みが必要

## 実装した機能

- ASP.NET Core Identityによるログイン、認証、認可
- ペット情報、健康ログ、予定、通院履歴の登録・更新・参照
- ペットに紐づく画像のアップロード、取得、削除
- 管理者ユーザーの開発環境限定セットアップ
- 入力値と環境設定を検証し、Productionでの不正な設定を起動時に検知

- **Azure SQL Database**: ペット、健康ログ、予定、通院履歴、認証情報を永続化
- **Key Vault + Managed Identity**: 接続文字列などの機密情報をアプリへ直接埋め込まずに参照

## 設計判断とトレードオフ

READMEに記録した判断と、その判断で引き受けた制約です。

### 無料枠を前提にAzureで公開する

App Service（Linux / Free F1）とAzure SQL Database（free offer）を使い、ポートフォリオとして公開し続けられるコストに抑えています。リソースを作る前にBudget Alertを設定し、月500〜1,000円を目安に通知を受け取ります。

- **優先したこと**: 継続して公開できるコストと、App Service・Azure SQL・Key Vault・Managed Identityという本番に近い構成の両立
- **引き受けた制約**: SLAやスケールアウトはない。アクセスが途切れた後は、初回表示やDBの再開待ちに時間がかかる。常時安定稼働が必要になったら、App ServiceをBasic以上へ、DBを有料の構成へ切り替える

### 機密情報はKey VaultとManaged Identityで扱う

接続文字列などの機密値はApp Serviceへ直接置かず、Key Vault参照で読み込みます。App ServiceのManaged Identityには、Key Vaultのシークレットを読み取る権限だけを付与しています。

- **優先したこと**: 機密値をアプリの設定やリポジトリに残さないこと
- **引き受けた制約**: 無料枠だけでは完結せず、Key VaultやStorage Accountには小額の従量課金が発生し得る

### 画像はApp Serviceの永続領域に保存する

Blob Storageのマウントは読み取り専用で、アップロードや削除の保存先に使えません。そのため初期リリースでは、`/home`配下の専用ディレクトリへ保存しています。

- **優先したこと**: 既存の`FileSystemImageStorageService`をそのまま使い、構成を増やさずに公開すること
- **引き受けた制約**: 保存容量とバックアップがApp Serviceに依存する。容量・CDN配信・他サービスとの共有が必要になったら、`IImageStorageService`の実装をBlob Storage向けに差し替えて移行する

### Data ProtectionキーをBlob StorageとKey Vault keyで保護する

App Service既定の保存先は、スロット間で共有されず、保存時の保護もありません。そのため本番では、Blob Storageへ永続化したキーをKey Vault keyで暗号化しています。

- **優先したこと**: 再デプロイ後も認証Cookieを正しく検証でき、キー自体も保護された状態で保存されること

### 本番Migrationはアプリ起動時に実行しない

本番Migrationは、レビュー後にGitHub Actionsのワークフローから1回だけ適用します。障害時は安易なDown Migrationではなく、既知の正常バージョンの再デプロイと、必要に応じたDBバックアップからの復元を基本方針にしています。

- **優先したこと**: スキーマ変更をレビューしてから、意図したタイミングで一度だけ適用すること
- **引き受けた制約**: アプリのデプロイとは別に、Migrationを適用する手順が1つ増える

## 品質保証とデプロイ

- GitHub Actionsでビルド、テスト、フォーマットチェックを実行
- Playwrightでログインなどの主要導線をE2E検証
- Azureへのデプロイ後にログイン・一覧表示・画像取得のスモークテストを実行
- Azureへの認証にはOIDCを使用し、長期間有効なデプロイ用シークレットを持たない
- Migrationとアプリデプロイを分離し、適用順序とロールバック条件を明文化

## 制約と今後の課題

- 画像の保存先をBlob Storageへ移すこと。`IImageStorageService`の実装差し替えで移行できる設計にしている
- Playwright E2Eの対象は、ログインなどの主要導線に絞っている。画面カバレッジの拡大は継続的に進める
